# Changelog

Every release of Network Analyser, newest first. Versions are SemVer 0.y.z ([#32](https://github.com/b-git-hub/network-analyser/issues/32)): a breaking change bumps the minor, anything else bumps the patch. See [docs/releasing.md](docs/releasing.md) for what counts as breaking and how a release is made.

The release workflow publishes a version's entry as its release notes, so every entry follows this template, enforced by `tests/unit/test_release_gate.py` and by the release gate:

- `## [0.y.z] - YYYY-MM-DD` (or `## [Unreleased]` while it is being written).
- `### Breaking changes` first, then `### Allow-list and Device Role`. Write `None.` under either when there is nothing to say. A breaking change says what the operator must do after upgrading, including any migration step.
- Then any of `### Added`, `### Changed`, `### Fixed`, `### Security`.

The workflow adds the system requirements, the unsigned-build warning, the download check, the sizes and the install steps itself.

## [Unreleased]

### Breaking changes

None.

### Allow-list and Device Role

None.

### Changed

- **Licence-suffixed PIDs now get Cisco answers** (#162): a PID such as `ISR4451-X/K9` was sent with its slash as `%2F`, which Cisco's gateway refuses, so the device read "could not check" for end-of-life, Suggested Release and Latest Release. The slash is now sent as it is, the only form Cisco answers. The PID pattern is unchanged, so nothing else can reach the path.
- **IOS XE SD-WAN devices are no longer matched as plain IOS-XE** (#147): decision #78 keeps IOS XE SD-WAN out of the Advisory Check, but only the 20.x controller release was excluded, so a controller-managed edge router on 17.x got IOS-XE Advisories that may not apply to it. `show version`'s `Router operating mode:` line is now read into `VersionFacts` and carried on each Visited Device as `router_operating_mode`, and a controller-managed device, or a 20.x controller, reads "could not check: IOS XE SD-WAN is not matched" instead. An autonomous-mode router is still matched as IOS-XE. `topology.json` gains the optional `router_operating_mode` field; no surface draws it, so no format-version bump.
- **Behaviour change: type 5 secrets are now flagged on IOS-XE too** (#142): the weak-secret-types Check raised type 5 (MD5-crypt) only on classic IOS. Research #76 says it is weak on IOS-XE as well, and the operator decided on #142 to flag it there, so an IOS-XE device with a type 5 secret now gets the High Finding it did not get before. NX-OS type 5 is SHA-256 and is still not flagged. A Platform that was not identified still reads "could not decide".

### Fixed

- **Legacy PAD and BOOTP are now flagged when they sit at their default, which is on** (#142): both were read only when the running config showed them, so a device that had never disabled them raised nothing. Cisco's IOS WAN Command Reference gives `service pad` the default "All PAD commands and associated connections are enabled", and the IOS Configuration Fundamentals Command Reference gives `ip bootp server` as "By default, the BOOTP service is enabled", so an absent line now counts as enabled and only `no service pad` / `no ip bootp server` read as off. The High legacy-services Finding therefore appears on IOS/IOS-XE devices that were silent before. NX-OS still lists only what its config shows, because neither default is proven there. The same review checked the IOS-XE vty default: Cisco's IOS XE configuration guides give the default `transport input` as Telnet, so a vty block with no `transport input` still raises the High Telnet Finding on IOS-XE as on classic IOS; no code change was needed.
- **A blank control-plane policy reply is now a Medium CoPP Finding, not "could not decide"** (#142): a device with no policy attached to the control plane answers `show policy-map control-plane` with a blank reply. The operator decision on #142 (2026-11-22) reads that as no policy applied, so the Medium is raised; a reply carrying a `%` line, or any other unrecognised reply with data, still reads "could not decide".
- **A refused new command's Finding now names both possible causes** (#142): the Medium assumed every refusal was an out-of-date Device Role. IOS also answers `% Invalid input detected` for a command its image does not have, and the error text cannot tell the two apart, so the Finding now reads "The Device Role may be out of date, or the image may not have the command: N Checks could not run (...)". The Check's name and id are unchanged, so report order and links keep working.
- **An IOS-XE 3.x device now gets its Advisories, Upgrade Target and Latest Release in Train** (#151): a device such as a Catalyst 3850 running `03.06.08E` had no entry in the family table, so it read "could not check" for Advisories and `not available` for the other two. IOS-XE 3.x releases are now in the family table, zero padding is stripped from an upper-case suffix too (`03.06.08E` becomes `3.6.8E`), and a 3.x Train keeps its letter (`3.6E`), so releases built for another image line are never lumped. The release pattern `advisories` checks before sending admits the same shapes. The spelling Cisco's openVuln and EoX APIs expect for a 3.x device is still to be confirmed by #164 item 5; the tool sends the normalised `3.6.8E` form. No command, allow-list entry or Device Role changes.
- **An NX-OS series Cisco's reply cannot resolve no longer reads as "no fix in Train"** (#136): an Advisory's `platforms[]` holding no single entry for the device's Nexus series, or two entries, left the Advisory Finding saying "No fix in Train T" with "move to a newer Train", while the device's Upgrade Target read `not available`. The fix is now unknown, not absent: the Finding reads "First fixed in Train T: not available (no single Cisco platform entry for this Nexus series)" with neutral advice, the Findings report callout reads `not available` rather than "Upgrade to not available or later", and its First fixed cell reads `not available` rather than "no fix in Train T". `cisco_detail` gains `fix_unresolved`, so `render` tells the two apart. One unresolved Advisory never makes another, resolved one claim "no fix".
- **The Run report and the Findings tab show both Latest Releases with their lifecycle codes** (#139): the Run report's Visited table gains a Latest Release column reading "Latest Release in Train: X (LC); overall: Y (LC)", the same words `findings.html` uses, and the Findings tab's Advisory detail pane shows "In Train: X (LC); overall: Y (LC)" under its Latest Release heading. `not available` and "running release is newer than Cisco's list" carry no code, because no listed release is there to describe. The 0.3.0 entry said the pane and the Run report showed the same values; they did not until this fix, and it now says what 0.3.0 shipped.
- **Every published IOS-XE Train from 16.6 on is classified as Standard- or Extended-Support** (#147): the Train support Check knew only 17.12 to 17.18, so a device on 17.9 or 26.1 gave a skipped Check and a device on 17.10 was never flagged. Cisco's rule from 16.6 on - every third Train is Extended-Support, the ones between are Standard-Support - now classifies 16.6 to 17.18, so 17.3, 17.6 and 17.9 raise nothing and 17.10, 17.11, 17.1, 17.2, 17.4 and 17.5 raise the Low Finding they should. A Train outside Cisco's published list, including the unconfirmed 26.x scheme, no longer skips the Check for the whole Run: that device gets its own Low "could not decide" Finding, so one unknown Train cannot hide another device's result.
- **An NX-OS device whose `show inventory` is refused still gets its Nexus series** (#159): when the Device Role does not allow `show inventory | json`, the series now falls back to the `Nexus<NNNN>` token `show version` prints (for example `Nexus9000`), so Advisory matching no longer stops at "hardware family not confirmed". The token is used only when it names exactly one documented series; it settles the series alone, never a chassis PID, so end-of-life, Suggested Release and Latest Release lookups are still not asked. No command, allow-list entry or Device Role changes.
- **Hardening config facts miss fewer insecure configs and raise fewer false results** (#142): cleartext `line` passwords, `enable secret level 15 5 ...` forms and type 7 in `key`, `key-string`, `md5` and `authentication-key` lines are counted; an NX-OS read-write community (`group network-admin`) is Critical when it has no ACL, and each community is counted once; NTP needs `ntp authenticate` and honours `ntp trusted-key 1 - 3`; only `logging host`, `logging server` and `logging <IP>` count as remote syslog; FHRP groups are counted per interface; OSPF and EIGRP authentication is judged per interface and BGP `password` under a neighbour or template is seen; `exec-timeout 0 30` is no longer a hit; ICMP counts skip shut-down and loopback interfaces; `aaa authentication enable ... none` counts as a fallback to none; `aaa authorization` counts as central only with a server group; `nxapi http port` with `feature nxapi` is a plain HTTP server; a device with no SNMP no longer raises a "could not decide" SNMPv3 Finding; the SSHv2 Check reads `show ip ssh`; and the NX-OS Guest Shell ("Deactivated") and SSH key-size (ECDSA-only) parsers read correctly. The four lower-confidence items this ticket also listed are now decided by the operator on #142, and code, [docs/config-facts.md](docs/config-facts.md) and this changelog agree.

## [0.3.0] - 2026-11-21

### Breaking changes

- `topology.json` is now format version 3: every Visited Device carries its advice record, including the count of Advisories its Upgrade Target does not clear, and the Upgrade Target is each Advisory's first fix above the running release rather than the newest fix in the Train. A 0.2.0 `render` would draw a partial target as if it cleared every Advisory, so it refuses a 0.3.0 Run folder; render an old Run folder with its own version. The 0.3.0 `render` still reads format versions 1 and 2 (#124; story 43).

### Allow-list and Device Role

None.

### Changed

- **Release order and Trains follow Cisco's numbering** (#123): a plain release sorts before its lettered or special build, and that sorts before the next release, so `17.12.7 < 17.12.7a < 17.12.7b < 17.12.8`, `26.1.2 < 26.1.2s1 < 26.1.3` and `10.6(3) < 10.6(3s) < 10.6(4)`. One sort key serves IOS-XE, NX-OS and classic IOS. A release's Train is its first two numbers (`17.12`, `10.4`); a classic IOS Train keeps its Train letter (`15.2E`), and an NX-OS release with an `I<n>` segment keeps that segment (`7.0(3)I7`, not `7.0`). The Consistency Checks, the Upgrade Target and the Latest Release all use this one rule.
- **The Upgrade Target is the first release that clears the Advisories** (#124): each Critical and High Advisory's fix is the lowest first-fixed release in the device's Train that is above the running release, and the target is the highest of those. Fixes at or below the running release count as no fix in the Train, and the tool still never picks another Train. When some Advisories have no fix in the Train, the target says how many it leaves open — "does not clear N Advisories: no fix in Train T"; when none is cleared it reads "no fix in Train T"; with no Critical/High Advisories it reads "no Critical/High Advisories". Each Advisory Finding's "first fixed in Train T" line uses the same per-Advisory rule, so the Finding and the target agree.
- **NX-OS devices get an Upgrade Target** (#126): it comes from each Advisory's `platforms[].firstFixes`, taken from the one entry whose name matches the device's own Nexus series, under the same per-Advisory rule and not-cleared count as IOS-XE. An unnamed entry is ignored, and no series, no matching entry or two matching entries give `not available` rather than a guess. Cisco's `platforms[].name` text is used for the Nexus 9000, 5000, 7000 and 3000 series; the Nexus 3000 mapping is an inference from Cisco's naming, and the Nexus 7700 and 2000 texts could not be confirmed, so those two series stay `not available`.
- **The Latest Release is Cisco's compatible list, not only its Suggested releases** (#127): it is the highest release, by version order, that the compatible-releases call lists for the device's chassis PID, shown both in the device's Train and overall with Cisco's lifecycle code beside each (for example `26.2.1 (ED)`). Every listed release counts, whatever its lifecycle or build, and dates are never used. A device running above everything listed reads "running release is newer than Cisco's list"; an unknown, rejected or unanswered PID, the 20-page cap or an outage reads `not available`, and the page cap is not a Needs-attention line. The Suggested Release Check and its call are unchanged, and no per-OS list such as `OS_data` is used.
- **The Findings report and the Map show the same advice** (#124, #127): the Findings report's Upgrade Target callout names the partial target and the count it leaves open, and its Latest Release reads "Latest Release in Train: X (LC); overall: Y (LC)"; the Map tag adds "(no fix in Train)" whenever an Advisory is left open, with the legend explaining the combined tag; and `topology.json` carries them, so `render` redraws every surface the same way. No surface layout changed.

### Security

- **The new lookup sends less, and proves it** (ADR 0007 amendment, 2026-11-21): the compatible-releases call sends one de-duplicated chassis PID per call, paged, and the NX-OS series alias joins the values that are pattern-checked before they are sent. `currentRelease` is never sent, so Cisco is never told which release a model runs. The Audit log counts calls, values and pages per endpoint and never records the PIDs or the alias themselves.

## [0.2.0] - 2026-11-21

### Breaking changes

- **Re-apply the Device Role before the first 0.2.0 Run: the allow-list gains new read-only commands.** IOS/IOS-XE gains `show inventory`, `show snmp user`, `show ntp associations`, `show policy-map control-plane`, `show ip ssh` and `show system insecure configuration` (IOS-XE 17.18.2 and later only); NX-OS gains `show inventory | json`, `show ntp peer-status | json`, `show copp status | json`, `show ssh key`, `show guestshell` and its fallback `show virtual-service list`. A Device Role generated before 0.2.0 refuses them, so the Checks that need them are skipped for that device and one Medium Finding, "Device Role is out of date: N Checks could not run", names them. Run `network-analyser role-snippet ios-xe` (or `nx-os`) and apply its output on every device, or AAA profile, that the tool logs into (#97, #98; stories 80 and 82).
- `topology.json` is now format version 2: it carries every Finding, Cisco's Advisory and EoX detail, and each device's advice. A 0.1.0 `render` refuses a 0.2.0 Run folder, so render an old Run folder with its own version; the 0.2.0 `render` still reads a 0.1.0 file (#93; story 113).
- **Cisco lookups are on by default** at the Run's end. A Run with no stored Cisco API Key prints one notice before the first prompt and ends with one Needs-attention line and exit code 1, keeping every Backup. Store a key with `cisco-key set` (once, locked with the Backup Passphrase), or pass `--cisco-lookups off` to keep the previous exit status (#104; story 35).

### Allow-list and Device Role

The 0.2.0 Analysis commands join each Platform's compiled-in allow-list ([spec #92](https://github.com/b-git-hub/network-analyser/issues/92) stories 78-79). **Re-apply the Device Role** from `network-analyser role-snippet ios-xe|nx-os` on every device before upgrading: a role from before 0.2.0 refuses the new commands, the Checks they feed are skipped for that device, and one Medium "Device Role is out of date" Finding names them. `role-snippet` prints every command below.

- IOS/IOS-XE, added by 0.2.0 (#97): `show inventory` (the chassis, stack-member, supervisor and line-card PIDs for EoX); `show snmp user` (SNMPv3 users and their crypto); `show ntp associations` (which peer, if any, the device syncs to); `show policy-map control-plane` (CoPP); `show ip ssh` (SSH's version and, on IOS-XE 17.11 or later, the host key's modulus); and `show system insecure configuration`, sent only to IOS-XE 17.18.2 or later, never to classic IOS. `show crypto key mypubkey rsa` is **not** allow-listed: where `show ip ssh` does not print the modulus, the SSH key-size Check is "could not decide", never a pass.
- NX-OS, added by 0.2.0 (#98): `show inventory | json`, `show ntp peer-status | json`, `show copp status | json`, `show ssh key`, and `show guestshell` with its fallback `show virtual-service list`. SNMPv3 users come from the running config; `show snmp user` is deliberately not on the NX-OS allow-list.
- The v1 allow-list is unchanged ([spec #37](https://github.com/b-git-hub/network-analyser/issues/37), #53). IOS/IOS-XE: `terminal length 0`, `terminal width 511`, `show version`, `show privilege` (#49); `show running-config view full`, the Backup, always the full view and never plain `show running-config` (#51); `show cdp neighbors detail`, `show lldp neighbors detail` (#50); and to collect the Topology's data (#59): `show interfaces`, `show interfaces switchport`, `show interfaces trunk`, `show ip interface`, `show etherchannel summary`, `show vlan brief`, `show vrf`, `show ip arp`, `show mac address-table`, `show ip ospf neighbor`, `show ip eigrp neighbors`, `show ip bgp summary`, `show ip route static`, `show standby brief`, `show vrrp brief`, `show glbp brief`, and for each VRF `show vrf` lists with IPv4 (a name of at most 32 letters, digits and `_.:-`): `show ip arp vrf <vrf>`, `show ip eigrp vrf <vrf> neighbors`, `show ip bgp vpnv4 vrf <vrf> summary`, `show ip route vrf <vrf> static`. The view permits each per-VRF form by its words before the VRF name.
- The v1 NX-OS allow-list is also unchanged: `terminal length 0`, `terminal width 511`, `show version`, `show user-account <username>` (the account's own name; #49); `show running-config`, the Backup (#51); `show cdp neighbors detail | json`, `show lldp neighbors detail | json` (#50); and to collect the Topology's data (#60), each with `| json` and for every VRF at once: `show feature | json`, `show interface | json`, `show interface switchport | json`, `show ip interface vrf all | json`, `show port-channel summary | json`, `show vlan brief | json`, `show vrf | json`, `show vpc brief | json`, `show vpc peer-keepalive | json`, `show ip arp vrf all | json`, `show mac address-table | json`, `show ip ospf neighbors vrf all | json`, `show ip eigrp neighbors vrf all | json`, `show ip bgp summary vrf all | json`, `show ip route static vrf all | json`, `show hsrp brief | json`, `show vrrp | json`.
- The new commands' output is treated like the running config: held in memory for the Run only and passed through the secret scan on its way to a record, an output or the Audit log (story 81). `show running-config all` is not added.

### Added

- Network Analyser v1 ([spec #37](https://github.com/b-git-hub/network-analyser/issues/37)): read-only discovery of Cisco IOS/IOS-XE and NX-OS devices over SSH, encrypted Backups of their running configuration, and a Topology diagram.
- VLAN Mismatches on each Link and Bundle in `topology.json` (#61): VLAN on one end only, differing native VLAN, trunk facing access, and differing access VLANs. A side with missing data is listed as skipped, not reported as a mismatch.
- **Analysis at the end of every Run** ([spec #92](https://github.com/b-git-hub/network-analyser/issues/92), #93, #94): every shipped Check runs on the data the Run already holds, so Analysis adds no device logins and an Unvisited Device gets none. Findings carry one scale, Critical / High / Medium / Low, a stable Check id and name, a Check type (Advisory, Configuration, Lifecycle, Consistency, Topology), what was found, what to do, and its source. A Check that cannot decide raises a Low "could not decide" Finding, never a pass.
- **Advisory Check** (#105): Cisco's Critical and High Advisories from openVuln, matched on release within classic IOS, IOS-XE or NX-OS, with one Finding per device per Advisory. Each gives the id and title, CVEs, SIR, CVSS, the published and updated dates, the device's release and the first-fixed release, the status "Affected release" and the fixed "matched on software release only" line. Each device also gets an **Upgrade Target** (the highest first-fixed release for its Critical and High Advisories, never outside its Train) and a **Latest Release**, as advice, not Findings. openVuln covers NX-OS only from July 2019, so an older NX-OS result says so.
- **Hardening Checks** (#96, #100, #101, #102): 27 configuration Checks from Cisco's hardening guides and its insecure-feature list. Each runs only where its feature is in use; six read show output through the new commands (SNMPv3 user crypto, NTP sync, CoPP, SSH key size, Guest Shell, and Cisco's own insecure list), and Cisco's `show system insecure configuration` items gain "also flagged by Cisco" on IOS-XE 17.18.2 or later. Findings name keywords, type numbers and counts, never a secret, hash, key, community string or config line.
- **Consistency Checks** (#99): the same model on different releases (Low, tool policy), stack or vPC peers on mismatched releases or modes (Medium), a Catalyst 9000 in bundle mode and IOS-XE on a Standard-Support Train (Low).
- **Lifecycle Checks** (#106): hardware EoX for the chassis, stack members, supervisors and line cards, and software EoX by release, each folded into one Finding per device at its worst level with dates and Cisco's replacement PID; a Low "not on a Suggested Release", and a Low "could not check" when Cisco returns nothing for the PID. Upcoming EoX dates are shown as device advice, not Findings.
- **v1's Findings on the new scale** (#93): conflicting evidence and "VLAN on one end only" are Low (the latter drawn fainter and listed last), and Bundle member mismatch, differing native VLAN, trunk facing access and differing access VLANs are Medium.
- **Cisco API Key** (#103): `cisco-key set` stores the client ID and secret at masked prompts after the Backup Passphrase, sends one token-only request to check them, and `--no-check` stores a key offline; it prints least-privilege guidance for Cisco's side. `cisco-key show` says whether a key is stored and when, and with the passphrase the last 4 characters of the client ID. `cisco-key remove` deletes it after `[y/N]`. The key file is locked with the Backup Passphrase, `change-passphrase` re-locks it, and deleting the check file deletes it too ([ADR 0008](docs/adr/0008-cisco-api-key-stored-locked-with-backup-passphrase.md)).
- **The Findings report, `findings.html`** (#107): one sheet per device, worst first, headed by hostname, management IP, model and release, opening with the Upgrade Target callout and the Latest Release, then the Advisories in one disclosure and the other Findings in one table with "Device Role out of date" first. Static, offline and script-free behind a CSP, with every device and Cisco string escaped. `render` redraws it from `topology.json`.
- **`--cisco-lookups on|off` and `--proxy host:port`** (#95, #104), with a matching run-file key. Lookups are on by default; `off` makes no outbound connection and never opens the key file. The Ready-to-start recap says whether lookups are on and whether a key is stored.

### Changed

- **Cisco is reached once, at the Run's end** ([ADR 0007](docs/adr/0007-cisco-lookups-at-run-end-after-secrets-wiped.md)): after every device session is closed, every Backup is locked and every Credential Set password and the Backup Passphrase are wiped. Only de-duplicated PIDs (chassis, stack members, supervisors, line cards) and OS type + release strings are sent, each checked against a strict pattern first. The one egress module, `advisories`, talks only to `id.cisco.com` and `apix.cisco.com` over HTTPS on port 443, checks certificates against the Windows store, refuses every redirect, uses Windows' proxy setting or `--proxy` and never an environment variable, batches (20 EoX, 10 Suggestion), paces under Cisco's limits, honours `Retry-After` and retries once. A rejected key is never retried. **Nothing Cisco returns is stored between Runs**: it is written only as this Run's Findings and advice, and the Audit log records how many calls and values went to each endpoint and the token result, never the values or the client ID. The Run report says Cisco's data was fetched over TLS and not signature-checked.
- A Cisco source that is down for the whole Run (no key, a rejected or expired key, or Cisco unreachable) gives one Needs-attention line per source, no per-device Findings for it, and exit code 1, with no new exit code. The Run still finishes and keeps its Backups.
- **The Findings tab in `diagram.html`** (#108): grouped by level (Critical → Low, with Critical, High and Medium open), one row per Check with its device count, filter chips per Check type, and an Advisory's id, title and SIR. Picking a Check lights only the devices and Links it hit and dims everything else; this replaces v1's "draw the neighbourhood" behaviour on this tab. The detail pane carries the Advisory's links, dates and affected-device table, or any other Check's level, source, "What to do" and where it was found. The tab's header says whether Cisco lookups ran and when. `diagram.drawio` is unchanged.
- **Map markers** (#109): a count badge coloured by each device's worst level, and a tag under the box for its Upgrade Target, "no fix in Train" or "? could not check", with the legend explaining both.
- **The Run report** (#110): the summary gives the total Findings and the count per level; Needs attention adds each Cisco source that was down, each "could not check", each Device Role out of date and the line "N Critical Findings from M Checks — see the Findings report"; the findings section gives the Finding and Check counts, a table of the Critical and High Checks (worst first, at most 10 rows) and a link to `findings.html`. v1's other sections are unchanged.
- The location notice for network, synced and removable Run folders names `findings.html` among the plaintext files.
- `topology.json` carries every Finding and each device's Advisory outcome, Upgrade Target, Latest Release and EoX details, so `render` redraws the diagram and the Findings report without a new Run.

### Security

- The Cisco client ID, client secret and bearer token are each held as a `Secret` and join the secret scan as soon as they exist; only `advisories` and `backup_store` may reveal them, which the import-rule test enforces. The key is never built into the exe or committed to the repo.
- Every Finding's text passes through the secret scan before it is written, as a backstop, and every Cisco reply is treated as untrusted and escaped wherever it is shown. Cisco's Advisory links are built by the tool from an id that passes the `cisco-sa-` pattern check.
- The new commands' output and the Cisco API Key follow the same rules as the running config and the Backup Passphrase: in memory for one Run, never read from the environment, never written in plaintext.
